## Contract C scope interpretation

Historical Contract C evidence matters here.

Contract C began explicitly as a **Claim Audit Lab → Decision Engine** epistemic-output boundary. The initial candidate already tracked a Decision Engine consumer, required producer/consumer conformance, and made a real Decision Engine consumer probe a pre-lock condition.

The later information-sufficiency program deliberately broadened the design question from the smallest projection needed by one MainFrame Gate to the smallest stable, decision-agnostic representation of CAL's epistemically meaningful result from which multiple materially different downstream decisions and human reports could be derived.

The promoted Contract C 1.0.0 therefore intentionally remains CAL-attributable. It preserves CAL-relevant execution, assessment, causal-basis, residual-state, and policy/config identity while excluding downstream materiality, risk, utility, routing, authority, and action state. Its promotion evidence included an independent Decision Engine clean consumer.

### Current interpretation

The evidence does **not** support the claim that Contract C is defective because it is CAL-specific.

A better architectural distinction is:

```text
CAL output
  -> Contract C 1.0.0
  -> Contract-C authority adapter
  -> Contract-C target resolver
  -> Contract-C policy semantics
                         \
                          -> domain-neutral Decision projection -> Contract D
                         /
other assessment authority
  -> its own authority adapter
  -> its own target resolver
  -> its own policy semantics
```

In other words, Contract C can remain the canonical epistemic result contract for CAL without becoming the universal input contract for Decision Engine.

## What else could explain the PASS?

1. **Policy duplication rather than a real seam.** The Contract-C research policy modules intentionally reexpress the maintained C policy semantics. Exact-byte reproduction therefore establishes boundary placement, not code reduction. The important observation is that this duplication remained outside the domain-neutral projection kernel.
2. **The tested C cases may be too narrow.** Seven cases cover CLEAR/HOLD/FAILED, two maintained policies, nested proposition/contribution targets, and important C state distinctions, but not every future Contract C state or policy.
3. **The projection kernel could still be accidentally overfit to Contract D 1.0.0.** That is currently acceptable because Contract D is the canonical Decision output authority. It would become a problem only if a future justified Decision output contract required a materially different projection responsibility.
4. **Authority admission remains heterogeneous.** This experiment does not show that Contract C admission and non-CAL assessment admission should share one generic ingress. Current evidence points the other way.

## Load-bearing assumption

The strongest remaining assumption is that an already-admitted authority + already-resolved exact target + domain policy result is a sufficiently stable common seam for Decision Engine.

That is narrower than assuming all upstream artifacts share one schema or trust root.

## Falsifiers for a successor

Before maintained extraction, a successor should try to break this seam by at least one of:

- mutation-test the projection kernel itself, especially policy dispatch, FAILED/effect exclusion, authority/target substitution, metadata non-authority, and exact Contract-D output;
- run a third materially heterogeneous authority domain with no assessment-authority shape reuse;
- pressure a Contract-C policy/target form that is not a top-level claim or current citation link;
- show that a legitimate Decision policy requires domain information the proposed seam cannot carry without kernel branching.

If any of those require Contract-C or domain vocabulary in the projection kernel, narrow or reject the abstraction rather than widening it opportunistically.

## Contract C evolution question remains separate

A different question remains open: whether Contract C 1.0.0 is too tightly coupled to the **current CAL implementation** for future CAL successors. Its original release explicitly did not claim arbitrary future-CAL compatibility, and the full CAL policy payload was retained because no separate immutable promoted lookup existed at the time.

That is a legitimate Contract-C evolution/minimality question, but this Decision Engine checkpoint provides no evidence that Contract C must be revised now.

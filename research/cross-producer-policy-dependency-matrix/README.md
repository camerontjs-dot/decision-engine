# Cross-Producer Contract-C Policy Dependency Matrix

## Classification

Draft Research Infrastructure / Decision Engine experiment.

This experiment does not modify maintained Decision Engine source, CAL source, Evidence Bundler source, Contract C, Contract D, Authorization, execution, release, tag, merge, or production defaults.

## Normative Contract C caveat

Contract C 1.0.0 is normatively CAL-specific. Its released specification defines the object as CAL-attributable state and defines `producer.semantic_implementation_sha` as the exact CAL semantic implementation commit.

Accordingly, the independent producer in this experiment is a **research structural shadow producer**, not a conforming production Contract C 1.0.0 producer. Validator acceptance is not treated as normative producer authorization.

The experiment asks a narrower Decision Engine question:

> When two independently implemented semantic producers present equivalent validator-accepted Contract-C-visible state over the same exact Contract B input and proposition, do the maintained Decision policies depend only on their declared C-visible predicates, or do they implicitly depend on producer family or other C fields?

## Exact base

Decision Engine base: `358c2bb20f490bf25e808434394b26a70a16a123`.

Frozen external authorities and research producers are pinned in the workflow.

## Same-input producer pair

Both producer families consume the same fresh Contract B bundle generated by the frozen CAL RC0 integration vertical for `PIPELINE_SMOKE_001`.

### Producer A — CAL

The frozen CAL integration producer emits its normal exact Contract C for `PIPELINE_SMOKE_001:child:1`.

### Producer B — independent structural shadow

A separate deterministic implementation reads only the exact Contract B bundle. For one requested proposition it emits `supported` only when exactly one retained Contract B evidence passage has text byte-equal to the exact proposition text. Zero or multiple exact matches produce `not_checkable`.

The shadow producer:

- imports no CAL module;
- consumes no CAL result, warrant, relation, measurement, or evaluator artifact;
- reads no evaluator gold;
- uses released Contract C code only for canonicalization and structural/reference validation after its semantic state is derived.

This is deliberately narrow. It is not a general entailment system and does not establish Contract C producer conformance.

## Matrix classes

Rows are classified before execution as one of:

- **NATURAL** — directly emitted by the producer under test;
- **VALID_COUNTERFACTUAL** — derived from the natural producer output, exact-validator accepted, but producer reachability is not claimed;
- **INVALID_CONTROL** — expected to fail exact ingress or target binding.

The distinction prevents a schema-valid mutation from being laundered into evidence that a real producer can or should emit that state.

## Valid counterfactual dimensions

Starting from each producer's natural `assessed / supported` atomic proposition, the matrix varies these dimensions one at a time where possible:

1. producer semantic implementation identity;
2. producer policy identity/payload;
3. eligibility assessment;
4. semantic-validity assessment;
5. aperture-completeness assessment;
6. temporal-applicability assessment;
7. measurement presence/value;
8. terminal branch identity;
9. reported verdict;
10. target contribution channel;
11. causal-basis versus residual membership;
12. proposition completion;
13. proposition execution;
14. result-set execution.

Every valid counterfactual is re-canonicalized, assigned a new content-derived `result_set_id`, and validated by the exact released Contract C 1.0.0 validator before Decision evaluation.

No proposition or evidence reference is changed by the valid counterfactual matrix. The same exact Contract B binding is preserved.

## Invalid controls

For both producer families the matrix also pressures:

- wrong external Contract C SHA;
- wrong expected Contract B binding;
- wrong Decision target content hash;
- invalid producer policy hash.

## Policy observations

The matrix records separately for the maintained policies:

- evaluation state;
- disposition;
- typed effect;
- reason codes;
- diagnostics;
- canonical Contract D validity;
- exact Contract D SHA.

Cross-producer equivalence ignores object-specific authority and target IDs but compares policy semantic signatures.

## Preregistered dependency hypotheses

Based only on maintained source inspection:

### Supported-claim verification

Expected load-bearing C dimensions:

- result-set execution state;
- target proposition execution state;
- target proposition completion;
- reported verdict.

- producer identity/policy;
- assessment-stage states;
- measurement;

Expected non-load-bearing dimensions for disposition/effect/reason:

- producer identity/policy;
- assessment-stage states;
- measurement;

- reported verdict;
- contribution channel.

## Falsifiers

The candidate producer-independent Decision kernel is weakened if any of the following occurs:

1. equivalent C-visible policy state produces different semantic Decision signatures across producer families;
2. a maintained policy changes disposition/effect/reason when only a preregistered non-load-bearing field changes;
3. a preregistered load-bearing mutation fails to change policy behavior as source inspection predicts;
4. producer identity itself becomes necessary to reproduce policy behavior;
5. the exact validator or maintained ingress rejects one producer family for a reason not explained by the released Contract C normative CAL-specific boundary;
6. a valid counterfactual requires changing more semantic dimensions than declared and the matrix cannot isolate the dependency.

## Non-claims

A passing result will not establish:

- that non-CAL producers conform to Contract C 1.0.0;
- arbitrary producer trust;
- semantic correctness of CAL or the shadow producer;
- producer reachability for counterfactual rows;
- a promoted generic Decision primitive;
- Authorization or execution;
- that Contract C 1.0.0 should be generalized rather than succeeded by a new contract.

## Promotion boundary

Keep Draft. No maintained refactor is justified by this matrix alone. A shared kernel, if later proposed, must survive mutation testing and at least one domain whose semantic authority is not claim-audit-specific.
